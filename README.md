# Astro/Tarot Bot — демо

Telegram-бот для бережных эзотерических сценариев: раскладов Таро, чтения
кофейной гущи по фото и разбора натальной карты. Пользователь пишет обычным
языком, а бот сам выбирает подходящий сценарий и ведёт диалог без перегруженного
меню.

## Архитектура

```text
Telegram update
      |
      +--> moderation.py ------------ блокировка явного abuse
      |
      +--> FSM (Redis / MemoryStorage) - короткое состояние сценария
      |
      +--> text ---------------------- llm_client.route_message()
      |                                  + tools.py function calling
      |
      +--> photo --------------------- llm_client.analyze_image()
      |                                  + scenarios/coffee.py
      |
      +--> scenarios/tarot.py -------- random draw, positions, image lookup
      +--> scenarios/natal.py -------- sun-sign demo calculation
      |
      +--> sessions.py --------------- SQLite profile, raw session, summaries
      +--> payments.py --------------- SQLite quotas, balances, payments
      |
      +--> generated answer ---------- LLM + Telegram HTML formatting
```

### Хранилища

- **Redis** — FSM: `TarotFlow`, `NatalFlow`, `ImageFlow`, follow-up. Включается
   через `REDIS_URL`, ключи имеют отдельный prefix и TTL.
- **SQLite** — платежи, балансы, бесплатные лимиты, блокировки, согласия,
   профиль и ограниченная память диалога. Это единый источник финансовых и
   пользовательских данных.
- **LLM** — маршрутизация и текстовая интерпретация; карты, лимиты и расчёт
   знака не выбираются моделью.

### Потоки

- Текстовый запрос без состояния проходит через function calling.
- Таро с вопросом запускается сразу; короткое «Таро» сначала уточняется.
- Фото классифицируется как coffee, natal или invalid через vision-модель.
- После результата доступны дополнительные вопросы по контексту услуги; каждый
   содержательный follow-up расходует один запрос.
- При ошибке генерации зарезервированный запрос возвращается.
- Webhook платежа проверяется и обрабатывается идемпотентно.

Минимальный рабочий скелет Telegram-бота, где LLM выступает
диспетчером интентов (function calling), а сами «гадания» —
детерминированный код.

## Как это работает

1. Пользователь пишет что угодно свободным текстом.
2. Если он **не в середине сценария** — сообщение уходит в LLM
   вместе со схемами функций (`tools.py`). Модель либо отвечает
   текстом (уточняющий вопрос), либо вызывает `start_tarot_reading`
   или `start_natal_chart`, если данных достаточно.
3. Диспетчер в `bot.py` смотрит на имя вызванной функции и запускает
   соответствующий сценарий (`scenarios/tarot.py`, `scenarios/natal.py`).
4. Сам расчёт — **не LLM**: карты Таро тянутся `random.sample`,
   знак зодиака вычисляется по датам. Никакой мистики, чистый Python.
5. LLM вызывается второй раз — только чтобы облечь готовые факты
   (выпавшие карты / знак) в живой персонализированный текст.
6. Если пользователь уже в сценарии (FSM state не пуст, например
   ждём дату рождения) — новый поход в LLM для роутинга не нужен,
   обрабатываем как следующий шаг сценария напрямую.

## Запуск

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt

cp .env.example .env
# заполнить BOT_TOKEN, LLM_BASE_URL (эндпоинт routercheap),
# LLM_API_KEY, LLM_MODEL (имя модели, доступной в твоём routercheap)

python bot.py
```

## Платежи

Команда `/buy` показывает пакеты запросов. Доступны Telegram Stars, ЮKassa и
xRocket Pay. Заполни платёжные переменные в `.env.example` и перенеси их в `.env`.

## Память диалога

При первом использовании бот просит согласие на хранение памяти. В SQLite
временно хранятся последние 15 реплик текущей сессии, профиль с датой рождения
и до 10 кратких summary прошлых сессий. Сырые реплики удаляются после сжатия.
Сессия закрывается после 3 часов бездействия или после 20 пар сообщений.
Команда `/new` немедленно очищает текущую историю и summaries, не вызывая LLM;
профиль, лимиты и платные остатки сохраняются.

Команда `/forget` (или `/delete_data`) удаляет профиль и историю диалогов.
Лимиты, платежи и реферальные данные сохраняются.

## Фото-сценарии

Бот принимает фото или JPG/PNG-файлы и сам определяет сценарий:

- чашка или блюдце с кофейной гущей — чтение символов и бережная трактовка;
- скрин/фото натальной карты — чтение видимых данных и уточняющие вопросы,
   если не хватает даты, времени или места рождения;
- неподходящее или нечитаемое изображение — понятная просьба прислать фото
   повторно. После трёх неподходящих изображений подряд включается временная
   блокировка на 3 часа.

Для vision-провайдера можно отдельно указать `LLM_VISION_MODEL`. Если поле
пустое, используется `LLM_MODEL`; выбранная модель должна поддерживать входные
изображения.

После завершённой услуги бот оставляет follow-up состояние для вопросов по
результату. Каждый содержательный вопрос в контексте Таро, натальной карты или
чтения гущи расходует один запрос; технические уточнения до оказания услуги не
тарифицируются. После пяти follow-up текущий контекст закрывается.

Базовый разговор ограничен 10 ответами в календарный день и хранится в SQLite,
поэтому `/new` и перезапуск не сбрасывают этот лимит. Предложение услуги
становится заметнее после 3-го ответа; после 10-го базовый чат ставится на паузу
до следующего дня или перехода к услуге. Успешно оказанная услуга сбрасывает
дневной счётчик базового разговора.

Источники трафика передаются через Telegram deep link, например
`https://t.me/имя_бота?start=instagram_sep`. Первый источник сохраняется после
перехода и доступен администратору в уведомлении о новом пользователе и по
команде `/refstats`. Допустимы латинские буквы, цифры, `_` и `-`, до 64 знаков.

Пользователь может получить личную реферальную ссылку командой `/referral`.
Если новый пользователь впервые открывает такую ссылку и принимает условия,
пригласившему начисляются 3 запроса. Бонус начисляется один раз на каждого
приглашённого, самоприглашение не учитывается. Приглашённому пользователю
достаточно принять условия; его первый рекламный источник при этом сохраняется.

Шаблон политики находится в `PRIVACY_POLICY_TEMPLATE.md`. Его нужно адаптировать
под оператора, провайдеров и обязательные сроки хранения до публикации.

Для ссылок на опубликованные документы используй:

```env
PRIVACY_POLICY_URL=https://твой-домен/privacy
PUBLIC_OFFER_URL=https://твой-домен/offer
```

Совершенно новый пользователь получает 2 стартовых запроса один раз. После
их расходования ему доступен 1 бесплатный запрос в календарные
сутки. Затем используются купленные запросы; бесплатная и платная квоты
учитываются раздельно. `/forget` не сбрасывает ни одну из этих квот.
Команда `/limits` показывает стартовый остаток (если он больше нуля), дневной
остаток, общий доступный баланс и платные запросы.

Базовый диалог ограничен 10 ответами за календарный день. Счётчик хранится в
SQLite и не сбрасывается командой `/new` или перезапуском бота; после успешной
услуги (Таро, натальный разбор, чтение гущи или follow-up по результату) дневной
счётчик базового диалога сбрасывается. День считается в UTC.

### Команды

- `/start` — запуск; параметр deep link может передать рекламный источник или
   код приглашения;
- `/limits` — остатки запросов;
- `/buy` — пакеты и способы оплаты;
- `/referral` — личная ссылка-приглашение; за нового пользователя, принявшего
   условия, пригласившему начисляются 3 запроса;
- `/new` — начать с чистого контекста, не сбрасывая лимиты и балансы;
- `/forget` или `/delete_data` — удалить профиль и историю диалогов;
- `/grant USER_ID КОЛИЧЕСТВО` — ручное начисление администратором;
- `/refstats` — статистика источников для администратора.

Для ручного начисления запросов администратору нужно указать свой Telegram ID
в `ADMIN_USER_IDS`, например `ADMIN_USER_IDS=123456789`, а затем использовать
`/grant USER_ID КОЛИЧЕСТВО`.

Бот поддерживает интерактивный выбор темы Таро и бережный стиль общения.
Явные попытки раскрыть промпт, обойти лимиты или тестировать внутреннюю
механику приводят к блокировке пользователя на 3 часа.

Для ЮKassa и xRocket нужен публичный HTTPS-адрес приложения:
`PAYMENT_WEBHOOK_URL` должен указывать на домен сервера. Webhook-маршруты:
`/payments/yookassa` и `/payments/xrocket`; прокси должен направить их на
`PAYMENT_WEBHOOK_PORT`.

Webhook нужен для автоматического подтверждения внешней оплаты. Telegram Stars
работают без нашего webhook: Telegram присылает боту `successful_payment`.
ЮKassa и xRocket проводят оплату вне Telegram, поэтому без webhook бот не
узнает, что счёт оплачен, и не начислит запросы. Для ЮKassa бот дополнительно
проверяет платёж через API, а для xRocket проверяет HMAC-подпись, версию и
свежесть уведомления.

Баланс и незавершённые платежи хранятся в SQLite-файле `PAYMENTS_DB_PATH`,
поэтому переживают перезапуск бота. SQLite подходит для одного процесса и
небольшой нагрузки. При запуске нескольких экземпляров или росте нагрузки
перенеси эти таблицы в Postgres. Для webhook-ов также добавь проверку подписи
или секретного токена на уровне прокси/middleware.

## Redis

Если задан `REDIS_URL`, FSM-состояния (`TarotFlow`, `NatalFlow`, follow-up и
ожидание фото) хранятся в Redis и переживают перезапуск процесса. При пустом
`REDIS_URL` используется временный `MemoryStorage`. Платежи, балансы, лимиты,
согласия и долговременная память остаются в SQLite и не зависят от Redis.

Для локального Redis достаточно указать:

```env
REDIS_URL=redis://127.0.0.1:6379/0
REDIS_KEY_PREFIX=astro_bot:fsm
REDIS_STATE_TTL_SECONDS=86400
REDIS_DATA_TTL_SECONDS=86400
```

`REDIS_KEY_PREFIX` изолирует ключи этого бота от других приложений в той же
Redis-базе. TTL удаляет заброшенные FSM-состояния и временные данные через
24 часа; платежи, лимиты и память диалога по-прежнему хранятся в SQLite.

## Структура

```
astro_bot/
├── bot.py              # aiogram, роутинг, диспетчер сценариев
├── config.py           # переменные окружения
├── llm_client.py       # обёртка над routercheap (OpenAI-совместимый API)
├── payments.py         # тарифы, счета и начисление запросов в SQLite
├── tools.py             # схемы функций для function calling
├── states.py            # FSM состояния
├── scenarios/
│   ├── tarot.py          # расклад Таро (random) + LLM-интерпретация
│   └── natal.py          # знак зодиака по дате + LLM-интерпретация
├── requirements.txt
└── .env.example
```

## Про routercheap

`llm_client.py` использует обычный `openai` SDK с переопределённым
`base_url`, поэтому подходит для любого OpenAI-совместимого роутера,
включая routercheap — просто укажи в `.env`:

```
LLM_BASE_URL=<эндпоинт твоего routercheap>
LLM_API_KEY=<ключ>
LLM_MODEL=<имя модели, которое принимает твой роутер>
```

Если у твоего конкретного инстанса routercheap нестандартный формат
ответа (не совпадает с OpenAI Chat Completions), правь только этот
один файл — остальной код от формата ответа провайдера не зависит.

## Что упрощено в демо и что доделать перед продакшеном

- **Натальная карта** — считается только знак Солнца по дате.
  Для настоящего разбора (Асцендент, дома, аспекты планет) нужна
  библиотека эфемерид (`pyswisseph` или `flatlib`), плюс запрос
  точного времени и места рождения + геокодинг.
- **Лимиты** — бесплатное использование и платный баланс хранятся в SQLite,
  дневной лимит автоматически разделён по датам и явно виден в `/limits`.
  Для нескольких инстансов бота перед продакшеном используй Postgres.
- **FSM storage** — `MemoryStorage`, в проде замени на
  `RedisStorage`, иначе состояния сценариев теряются при перезапуске
  и не масштабируются на несколько инстансов бота.
- **Оплата** — реализованы Telegram Stars, ЮKassa и xRocket Pay; перед
  продакшеном добавь юридические документы и проверку webhook-подписей.
- **Колода Таро** — в проекте 78 карт; изображения добавляются по списку
  из `images/tarot/README.md`.
